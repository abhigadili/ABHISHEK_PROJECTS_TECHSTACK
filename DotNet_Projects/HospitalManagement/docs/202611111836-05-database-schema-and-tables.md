# 5. Database schema and table details

MySQL (the **existing** local server, port 3306, user `abhig`), one database per microservice, one `DbContext` per service, schema owned by **EF Core migrations**. A service only ever connects to its own database; there are **no foreign keys across databases** - other services' ids (`PatientId`, `DoctorId`, `UserId`, `HospitalId` ...) are plain logical columns validated through the owning service's API (gRPC / HttpClient).

|---|---|---|---|
| HospitalDB | Hospital Service / `HospitalDbContext` (IdentityDbContext) | hospitals, departments, users, roles, user_roles, user_claims, user_logins, user_tokens, role_claims | `database/scripts/11-HospitalDB-migrations.sql` |
| PatientDB | Patient Service / `PatientDbContext` | patients, outbox_messages, inbox_messages | `12-PatientDB-migrations.sql` |
| DoctorDB | Doctor Service / `DoctorDbContext` | doctors, doctor_schedules, doctor_unavailability | `13-DoctorDB-migrations.sql` |

| MedicalRecordsDB | Medical Records Service / `RecordsDbContext` | patient_records, record_entries, outbox_messages, inbox_messages | `15-MedicalRecordsDB-migrations.sql` |
| PrescriptionDB | Prescription Service / `PrescriptionDbContext` | prescriptions, prescription_items, outbox_messages, inbox_messages | `16-PrescriptionDB-migrations.sql` |

Plus one history table per database, `__hdn_migrations_history`. **Total: 44 `hdn_` tables + 10 history tables.** `outbox_messages` / `inbox_messages` are the reliable-messaging tables (see the Kafka document); the Hospital and Doctor services publish/consume nothing and therefore have none.

## These databases are shared with the Java build and (NotificationDB) other applications
The `HospitalManagement` Java version of this system already created and uses the same nine databases (`PatientDB`, `DoctorDB`, ... with its own unprefixed tables such as `patients`, `users`, `outbox_events`), and `NotificationDB` additionally holds tables of two student-management applications (`Notifications`, `Email_Logs`, `sms_*`, `dn_*`, `__EFMigrationsHistory`, `flyway_schema_history`, ...). To honour "do not modify existing databases or data":
* every table of this .NET build is prefixed **`hdn_`** and the EF history table is **`__hdn_migrations_history`** (EF's default `__EFMigrationsHistory` is never used or created);
* **foreign-key constraint names are prefixed `fk_hdn_`** - in MySQL a constraint name is unique per *database*, and the first migration run failed on the Java build's `fk_department_hospital` until this was done;
* the migrations contain **no `ALTER DATABASE`** (Pomelo's default first step `ALTER DATABASE ... CHARACTER SET utf8mb4` was removed from every migration so no database default is ever changed);
* nothing outside `hdn_*` / `__hdn_migrations_history` is read, altered or dropped. `scripts/verify-db.sh` is read-only.
(The first, failed run created a few partial `hdn_*` tables in HospitalDB; those - and only those - were dropped and recreated, and the database default collation that run had changed on the two databases it touched was restored to the original `utf8mb4_unicode_ci`.)

## How the schema is created and verified
* `database/scripts/00-create-databases.sql` - ten `CREATE DATABASE IF NOT EXISTS` statements (utf8mb4), nothing is recreated or dropped.
* `database/scripts/11..20-*-migrations.sql` - **idempotent EF Core migration scripts** (`dotnet ef migrations script --idempotent`, regenerated by `scripts/generate-sql.sh`). Re-running skips applied migrations. Each script was applied twice to a throw-away database per service (44 tables, no errors) and the scratch databases dropped.
* `scripts/create-databases.sh` applies them. The services **also apply their own migrations at start-up** (`Database.MigrateAsync()` with retry), so either path works and they are compatible (same history table).
* `scripts/verify-db.sh` checks connectivity and the `hdn_` table count per service. Each service connects with its own connection string (`Database:Name` + `MYSQL_*` env variables - the password is only ever read from the environment).

## Modelling notes
* **Keys:** `BIGINT AUTO_INCREMENT`. Business numbers (`BillNumber`, `TransactionRef`, `AccessionNumber`) have unique indexes. **Money:** `DECIMAL(10,2)` / `(12,2)`. **Times:** `date`, `time(6)`, `datetime(6)` (UTC for instants). **Enums** are stored as strings.
* **Integrity rules in the schema:** `hdn_patients` unique `UserId`/`Email`/`Phone`/`IdentityNumber`; `hdn_doctors` unique `LicenseNumber`/`Email`/`UserId`; `hdn_appointments.SlotKey` unique while booked (NULL when cancelled/missed - concurrent bookings of one slot cannot both succeed); `hdn_bills` unique `(ReferenceType, ReferenceId)`; `hdn_payments.TransactionRef` and `ActiveBillId` (one in-flight payment per bill); `hdn_pharmacy_orders.PrescriptionId`; `hdn_lab_requests.AccessionNumber`; `hdn_lab_reports.RequestId`; `hdn_record_entries (EntryType, ReferenceType, ReferenceId)`; `hdn_inbox_messages (EventId, Consumer)`.
* **Foreign keys** exist only inside a database: departments->hospitals, schedules/unavailability->doctors, record_entries->patient_records, prescription_items->prescriptions, lab_requests->lab_tests, lab_reports->lab_requests, bill_items/payments->bills, order items->orders/medicines, ASP.NET Identity relations.
* **Concurrency:** unique indexes for slots/payments/bills, `SELECT ... FOR UPDATE` row locks for pharmacy stock (no row-version tokens - MySQL has no automatic rowversion).
* **Indexes** target the real queries: doctor search, appointment lookup by doctor+date and patient, reminder scan `(Status, ReminderSent, AppointmentDate)`, bills by patient and `(Status, DueDate)`, payments by `(Status, InitiatedAt)`, notifications by recipient/event/status, outbox `(SentAt, Id)`.
