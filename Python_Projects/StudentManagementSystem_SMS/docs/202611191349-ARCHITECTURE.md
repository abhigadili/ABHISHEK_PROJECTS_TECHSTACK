# Architecture

Student Management System (SMS) — six independently deployable FastAPI services, five MySQL databases, one Kafka cluster.

## 1. The big picture

```
                                   ┌───────────────────────────────────────────────┐
   Browser / Postman / curl        │                  API GATEWAY :8000            │
   ───────────────────────────────▶│ request-id / correlation-id · CORS · security │
                                   │ headers · JWT check (+revocation cache) ·     │
                                   │ SlowAPI rate limits · retry/timeout · proxy   │
                                   └──┬──────────┬──────────┬──────────┬──────────┬┘
                       REST (HTTPX)   │          │          │          │          │
                                      ▼          ▼          ▼          ▼          ▼
                               ┌──────────┐┌──────────┐┌──────────┐┌────────────┐┌──────────────┐
                               │   AUTH   ││ STUDENT  ││  COURSE  ││ ENROLLMENT ││ NOTIFICATION │
                               │  :8001   ││  :8002   ││  :8003   ││   :8004    ││    :8005     │
                               │ sync ORM ││ async ORM││ async ORM││  async ORM ││  async ORM   │
                               └────┬─────┘└────┬─────┘└────┬─────┘└──┬───────┬─┘└──────┬───────┘
                                    │           │           │         │       │         │
                          AuthDB ───┘  StudentDB┘ CourseDB ─┘  EnrollmentDB   │  NotificationDB
                                                                              │
              Synchronous REST between services (HTTPX):                      │
                Enrollment ──GET /students/{id}|me──▶ Student                 │
                Enrollment ──GET /courses/{id}─────▶ Course   (gather)        │
                Course ─────GET /users/{id}────────▶ Auth  (teacher check)    │

   ┌──────────────────────────────── Apache Kafka (KRaft) ───────────────────────────────────┐
   │ sms.auth.events   sms.student.events   sms.course.events   sms.enrollment.events        │
   │ sms.notification.requests            (+ one <topic>.dlq dead-letter topic for each)     │
   └──────────────────────────────────────────────────────────────────────────────────────────┘
        ▲ outbox relay (Auth, Student, Course, Enrollment publish)   ▼ consumers (see §5)
```

* **Clients only ever talk to the gateway.** Services are also published on their own ports for development, Swagger access and the verification scripts.
* **Each service owns its database.** There are *no* cross-database foreign keys and no service ever reads another service's tables.
* **Two communication styles, used for different jobs:**
  * *Synchronous REST* when the caller needs the answer **now** to decide (is this student active? does the course have seats? is this user a teacher?).
  * *Asynchronous Kafka events* when the caller only needs to **announce a fact** and other services react (a student enrolled → update counters, send an e-mail).

## 2. Services and responsibilities

| Service | Port | Database | DB access | Responsibility |
|---|---|---|---|---|
| **api-gateway** | 8000 | — | — | Single entry point. Correlation ids, CORS, security headers, JWT validation (signature, expiry, issuer, type, **revocation**), rate limiting, streaming reverse proxy with timeout/retry, merged OpenAPI/Swagger, aggregated health. |
| **auth-service** | 8001 | `StudentManagementAuthDB` | **sync** SQLAlchemy (+ async engine for the outbox relay only) | Registration, login, JWT access/refresh tokens, OAuth2 password flow with scopes, refresh rotation + reuse detection, logout/revocation, password change/forgot/reset, lock-out, RBAC, user & role management, optional OIDC login. |
| **student-service** | 8002 | `StudentManagementStudentDB` | **async** (+ one sync engine for the report endpoint) | Student CRUD, profile (1‑1), contacts (1‑N), interests (N‑M), departments, search/filter/sort/pagination, bulk operations, statistics, profile picture and documents. |
| **course-service** | 8003 | `StudentManagementCourseDB` | async | Courses, categories, credits/duration/capacity, availability, teacher assignment (association object), course documents. |
| **enrollment-service** | 8004 | `StudentManagementEnrollmentDB` | async | Enroll/cancel/complete, duplicate + capacity protection, status history, per-student/per-course queries, statistics. |
| **notification-service** | 8005 | `StudentManagementNotificationDB` | async | Consumes events, queues notifications, renders HTML + text templates, sends e-mail (SMTP/file/console) asynchronously with retry/back-off, notification history. |

`libs/sms_common` is a *library*, not a service: configuration, logging, middleware, errors, JWT/security dependencies, DB sessions, pagination, outbox, Kafka producer/consumer, HTTP client, storage abstraction, background-task manager. Services depend on it; it knows nothing about any service's models.

## 3. Database ownership

| Database | Owner | Tables |
|---|---|---|
| `StudentManagementAuthDB` | auth-service | `users`, `roles`, `user_roles`, `refresh_tokens`, `password_reset_tokens`, `outbox_events` |
| `StudentManagementStudentDB` | student-service | `students`, `student_profiles`, `contact_infos`, `departments`, `interests`, `student_interests`, `student_files`, `outbox_events`, `processed_events` |
| `StudentManagementCourseDB` | course-service | `courses`, `categories`, `course_teachers`, `course_files`, `outbox_events`, `processed_events` |
| `StudentManagementEnrollmentDB` | enrollment-service | `enrollments`, `enrollment_status_history`, `outbox_events`, `processed_events` |
| `StudentManagementNotificationDB` | notification-service | `notifications`, `notification_attempts`, `processed_events` |

Cross-service references (`students.user_id`, `enrollments.student_id`, `enrollments.course_id`, `course_teachers.teacher_user_id`) are **plain integers**. Where a service needs a human-readable value of a foreign entity it stores a **snapshot** (the enrollment row carries the student's name/e-mail/number and the course code/title/credits) and refreshes it from `StudentUpdated` / `CourseUpdated` events. Full schemas: [DATABASE.md](202611191349-DATABASE.md).

## 4. Synchronous communication (REST over HTTPX)

| Caller | Callee | Call | Why it must be synchronous | Code |
|---|---|---|---|---|
| Gateway | every service | proxied request | it *is* the request | `services/gateway/app/proxy.py` |
| Enrollment | Student | `GET /students/{id}` (staff) or `GET /students/me` (student) | enrolling requires an existing, `ACTIVE` student | `enrollment/app/services.py::enroll` |
| Enrollment | Course | `GET /courses/{id}` | requires an `OPEN` course with free seats | same |
| Course | Auth | `GET /users/{id}` (admin token forwarded) | assigning a teacher requires a real, active `TEACHER` | `course/app/services.py::assign_teacher` |
| Auth | external IdP | OIDC discovery / token / userinfo | OIDC callback (sync HTTPX client) | `auth/app/api/v1/oidc.py` |

`sms_common/http_client.py` gives every call: pooled connections, separate connect/read timeouts, **bounded retries only for idempotent methods** (GET/HEAD/PUT/DELETE/OPTIONS) on connection errors, timeouts and 502/503/504 with exponential back-off + jitter, `X-Correlation-ID` propagation (new `X-Request-ID` per hop), bearer-token forwarding, and mapping of downstream failures to our own error envelope (404 → 404, outage → 503, timeout → 504).

`enroll()` fires the student and course lookups **concurrently** with `asyncio.gather`, so latency is `max(a, b)` instead of `a + b`.

## 5. Asynchronous communication (Kafka)

### Event flow

```
 Auth ────────UserRegistered, TokenRevoked───────────▶ sms.auth.events ───────▶ Gateway (revocation cache, one group per instance)
 Auth ────────NotificationRequested (welcome, password_reset, password_changed)──▶ sms.notification.requests ──▶ Notification
 Student ─────StudentCreated / Updated / Deleted─────▶ sms.student.events ────▶ Notification (StudentCreated → e-mail)
                                                                           └──▶ Enrollment (Updated → snapshot, Deleted → cancel enrollments)
 Course ──────CourseCreated / CourseUpdated──────────▶ sms.course.events ─────▶ Enrollment (CourseUpdated → snapshot)
 Enrollment ──StudentEnrolled / EnrollmentCancelled──▶ sms.enrollment.events ─▶ Course   (enrolled_count ±1)
                                                                           ├──▶ Student  (enrolled_courses_count ±1)
                                                                           └──▶ Notification (confirmation / cancellation e-mail)
```

| Topic | Key | Partitions | Producers | Consumer groups |
|---|---|---|---|---|
| `sms.auth.events` | user id | 3 | auth | `gateway-<host>-<rand>` (one per gateway instance) |
| `sms.student.events` | student id | 3 | student | `notification-service`, `enrollment-service` |
| `sms.course.events` | course id | 3 | course | `enrollment-service` |
| `sms.enrollment.events` | course id | 3 | enrollment (also on student deletion) | `course-service`, `student-service`, `notification-service` |
| `sms.notification.requests` | user id | 3 | auth | `notification-service` |
| `<topic>.dlq` | original key | 1 | any consumer that gives up | operators |

Details (payloads, headers, retry, DLQ): [KAFKA_DOCUMENTATION.md](202611191349-KAFKA_DOCUMENTATION.md).

### The Transactional Outbox (why no event is ever lost or invented)

```
HTTP request ─▶ service layer ─ BEGIN ─────────────────────────────────────────────┐
                               UPDATE enrollments ...      ┐ same DB transaction   │
                               INSERT outbox_events (...)  ┘                       │
                               COMMIT ─────────────────────────────────────────────┘
                                                    │
        OutboxRelay (background task, polls / is woken)
          SELECT … WHERE status='PENDING' ORDER BY id LIMIT n FOR UPDATE SKIP LOCKED
          producer.send_and_wait(topic, body, key)   (acks=all, idempotent producer)
          UPDATE status='SENT'                       ← crash here ⇒ re-sent ⇒ at-least-once
```

* Writing to the DB and to Kafka cannot be one atomic operation. The outbox row *is* part of the business transaction, so the event exists **iff** the data change committed.
* Delivery is **at-least-once**. Every consumer therefore records `(event_id, consumer_group)` in `processed_events` **in the same transaction as its own change**; a duplicate hits the primary key and is skipped (idempotent consumer). Verified: the same event sent 3× produces exactly one e-mail.
* `FOR UPDATE SKIP LOCKED` lets several instances of a service run the relay without double-sending.
* Order is preserved per message key because the relay stops its batch at the first failure.

## 6. Cross-cutting concerns

### Middleware order (identical in every service, `sms_common/middleware.py`)

```
request ─▶ RequestContext ─▶ AccessLog ─▶ Timing ─▶ SecurityHeaders ─▶ CORS ─▶ ErrorHandling ─▶ router ─▶ [SlowAPI*] ─▶ handler
response ◀──────────────────────────────── (same chain, reverse) ◀────────────────────────────────────────────────────
                          * gateway only: SlowAPI is applied as decorators on the proxy routes (route level, after routing);
                            exceeding a limit raises RateLimitExceeded → our handler returns the standard 429 envelope + Retry-After
```

* **RequestContext** is outermost: it accepts/creates `X-Request-ID` and `X-Correlation-ID`, stores them in `contextvars`, echoes them in the response, and thereby tags *every* later log line.
* **AccessLog** wraps **Timing**, so the duration it logs includes everything inside.
* **ErrorHandling** sits *inside* CORS, so even an emergency 500 carries CORS headers.
* Outside production the order is observable: `X-Middleware-Trace: ErrorHandling,SecurityHeaders,Timing,AccessLog,RequestContext` (innermost first, the order in which each layer sees the response). Verified by the e2e suite.
* All middleware are pure ASGI classes (not `BaseHTTPMiddleware`) so streaming responses stay streaming and `contextvars` survive.
* **Authentication is *not* done in middleware.** Doing it in both middleware and dependencies would duplicate responsibility. The gateway validates tokens as a coarse early filter (it needs revocation + public-path rules); each service enforces *authorization* (roles, scopes, ownership) with FastAPI dependencies (`SecurityDeps`).

### Errors

Every error — validation, domain, auth, rate limit, downstream outage, unexpected exception — uses one envelope:

```json
{"error": {"code": "NOT_FOUND", "message": "Student 7 not found", "details": [],
           "request_id": "…", "correlation_id": "…", "timestamp": "2026-11-19T08:01:17+00:00",
           "path": "/api/v1/students/7"}}
```

### Logging

JSON (or text) logs with timestamp, level, service, `request_id`, `correlation_id`, `user_id`, logger and message. A redaction filter masks JWTs, `Bearer …` and `password=/token=/secret=` pairs. Validation errors never echo password fields. The e2e suite greps all service logs after the run: no JWTs, no passwords.

### Configuration

Pydantic Settings: environment variables → project `.env` → defaults. **Secrets have no defaults** (`MYSQL_PASSWORD`, `JWT_SECRET`): a service refuses to start without them.

## 7. Design decisions and trade-offs

| Decision | Why | Trade-off / what changes in production |
|---|---|---|
| HS256 shared secret for JWT | Simple, fast, no key distribution in a learning project | Every service can *mint* tokens. Production: RS256/ES256, Auth holds the private key, others fetch a JWKS. |
| Access tokens are stateless; revocation via Kafka → gateway cache | Instant logout without a DB lookup per request | Calls that bypass the gateway are only protected by the 15‑minute expiry. Gateway cache is rebuilt by replaying the topic on start. |
| Auth uses **sync** SQLAlchemy | Argon2 hashing is CPU-heavy; a `def` endpoint runs in the threadpool and never blocks the loop | Two engines in Auth (sync for requests, async only for the relay). |
| Other services use **async** SQLAlchemy | I/O-bound; many concurrent requests per process | `lazy="select"` relationships cannot lazy-load in async, so loading is explicit (`joinedload`/`selectinload`) and rows are re-read after commit. |
| `GET_LOCK` advisory lock for enrollment capacity | Count + insert must be atomic across instances; there is no row to `SELECT … FOR UPDATE` before the first enrollment | Lock per course serialises enrollments of that course only. Verified: 8 concurrent requests, 3 seats → exactly 3 succeed. |
| Rate-limit counters in memory | No extra infrastructure | Per-instance. Point SlowAPI `storage_uri` at Redis for several gateway replicas. |
| Event replay on every consumer start (`auto_offset_reset=earliest`) | A new service instance/group sees history | Handlers must be idempotent (they are). |
| Single Kafka broker, replication factor 1 | Local/dev | Production: ≥3 brokers, RF 3, `min.insync.replicas=2`. |
| Snapshots in `enrollments` | Notifications and lists need no cross-service calls | Eventually consistent (seconds) with the source of truth. |

## 8. Traced request: *enroll a student* (real log excerpts)

`POST /api/v1/enrollments {"student_id": 1, "course_id": 1}` with an admin token:

1. **Gateway** — `RequestContext` creates `X-Correlation-ID`; `limiter` counts `user:1`; `authenticate()` verifies signature/expiry/issuer/type and checks the revocation cache; the proxy forwards with a *new* `X-Request-ID` and the same correlation id.
2. **Enrollment** — `Writer` dependency checks scope `enrollments:write`. `asyncio.gather` calls `student-service GET /students/1` and `course-service GET /courses/1` (each one runs the *same* JWT validation with the forwarded bearer token).
3. Rules: student `ACTIVE`, `course.is_available` → else `409`.
4. `named_lock("sms:enroll:course:1")` → duplicate check (`uq_enrollment_student_course`) → local active count `< capacity` → INSERT `enrollments` + history row + `outbox_events(StudentEnrolled)` → `COMMIT` → `201`.
5. **Relay** publishes `StudentEnrolled` to `sms.enrollment.events` (≈ 100 ms later).
6. Three consumer groups, three independent transactions, each guarded by `processed_events`:
   * **course-service**: `enrolled_count + 1` (so `available_seats` drops),
   * **student-service**: `enrolled_courses_count + 1`,
   * **notification-service**: `notifications` row (`enrollment_confirmation`) → dispatcher renders and sends the e-mail.
7. Every log line of every service for this journey contains the same `cid=` (checked by the e2e suite).

Realistic result a few hundred milliseconds later: `GET /courses/1` → `"enrolled_count": 1, "available_seats": 1`, and `GET /notifications` shows the confirmation as `SENT`.
