# Architecture

## 1. Big picture

```
 Client ──► hr-api-gateway :9080 ──► service (own port) ──► its own MySQL database
              │  JWT check, rate limit, CORS,            │
              │  correlation id, access log              ├──► Redis   (cache, locks, tokens)
              ▼                                           ├──► Kafka   (events, outbox)
        Redis (rate limit, revoked jti)                   └──► other services (OpenFeign / WebClient)
```

* **One entry point.** Only the gateway is meant to be exposed. It authenticates (JWT), authorises by path and role, rate-limits per user / IP, adds a correlation id and routes `/api/v1/<area>/**` to the owning service.
* **One database per service.** 15 MySQL databases (`hr_*_db`). No cross-database foreign keys and no service ever reads another service's tables; relations across services are UUID references resolved through APIs or events.
* **Two communication styles.**
  * *Synchronous* (need the answer now): OpenFeign (blocking, declarative) and WebClient (non-blocking, parallel) - see `feign-webclient-guide`.
  * *Asynchronous* (state changed, tell the others): Kafka events published through a **transactional outbox** and consumed **idempotently** - see `kafka-guide`.
* **Defence in depth.** The gateway validates the JWT, and every service validates it again (same HS256 key, plus a Redis revocation check). Method security (`@PreAuthorize`) and ownership checks inside the services are the last line.

### What lives in `common-library` (and why only that)

| Package | Content |
|---|---|
| `security` | `JwtAuthenticationFilter`, `CommonSecurityConfig`, `CurrentUser`, `AuthorizationService` (`@authz`), `TokenRevocationChecker` |
| `web` | `CorrelationIdFilter`, `RequestLoggingFilter`, `RequestHeaderValidationFilter`, 3 interceptors, request-scoped `RequestContext`, `ServiceInfoServlet`, `PageResponse` / `PageRequests` |
| `exception` | business exceptions and `GlobalExceptionHandler` (`@RestControllerAdvice`) |
| `persistence` | `BaseEntity`, `SoftDeletableEntity`, `CrudService`, `BeanMapper`, AES-GCM converter |
| `audit` | `AuditHistory`, `AuditService`, `AuditController` |
| `events`, `kafka` | event records (`HrEvents`), topics, `EventPublisher` (outbox), `OutboxRelay`, `IdempotentEventProcessor` |
| `cache` | Redis `CacheConfig`, `CacheEvictor`, `DistributedLockService` |
| `client` | `FeignGlobalConfig` (header propagation, `ErrorDecoder`, retry), `HrWebClient` |
| `async`, `storage`, `validation`, `openapi`, `util` | bounded executor, `FileStorage`, shared validators, Swagger config, SQL / log helpers |

Business entities and logic of one service are **never** placed in another module.

## 3. Layering inside a service

`controller` (HTTP only) → `service` (all business logic, transactions, authorisation rules) → `repository` (Spring Data / JdbcTemplate / JDBC) → MySQL. Plus `dto` (records), `entity`, `client` (Feign / WebClient), `producer` / `consumer` (Kafka), `scheduler`, `validation`, `engine` / `queue` / `pdf` where a service needs them.
Controllers contain no business rules; entities are never returned from APIs (DTO records + `BeanMapper`).

## 4. Request flow

`Client → Gateway → Security (JWT) → servlet filters → DispatcherServlet → HandlerMapping → HandlerInterceptors → Controller → Service → Repository → MySQL` - detailed with the actual classes in `servlet-request-pipeline`.

## 5. Data consistency without distributed transactions

| Problem | Solution used |
|---|---|
| Save data **and** publish an event atomically | *Transactional outbox*: the event row is written in the same DB transaction (`outbox_events`, `sent_at` NULL until delivered); it is sent right after commit and re-sent by `OutboxRelay` if the broker was down |
| The same event delivered twice | `processed_events` ledger keyed by (event id, consumer): `IdempotentEventProcessor` skips duplicates in the same transaction as the handler's work |
| Another service needs data it does not own | Local **read models** fed by events (`org_employee_nodes`, `leave_employees`, `rpt_employees`, `holiday_snapshots` ...) instead of cross-service joins |
| Two requests changing the same balance / sheet | Optimistic locking (`@Version`), pessimistic `SELECT ... FOR UPDATE` where a check-then-write must be exclusive (leave balance, employee code counter), Redis distributed locks for cross-instance workflows |
| Out-of-order events | status ranks in the reporting upserts; sequence-safe state machines in the owning services |

## 6. Resilience choices

* Feign: connect 2 s / read 8 s, retries only on I/O errors and 502/503/504 (3 attempts, 200 ms back-off), downstream 4xx mapped to the same exception type locally; all Feign calls in this project are idempotent reads.
* WebClient: timeout + `retryWhen` for GET, `onErrorResume` / `onErrorReturn` for optional sections (dashboards degrade section by section).
* Redis outage: caches fall through to MySQL (errors logged, never thrown); revocation check fails open (short access-token life); rate limiter fails open.
* Kafka outage: events stay in the outbox and are delivered later.
* Bounded thread pool (`hrExecutor`) with caller-runs back-pressure - never a thread per request.

## 7. Key design decisions

1. **UUID primary keys** (`char(36)`) so references can travel between services and be created without a sequence.
2. **Soft deletion** (`deleted` flag + `@SQLRestriction`) for master data; append-only audit table protected by MySQL triggers.
3. **Least-privilege DB access:** Flyway uses a migration login; applications use `hr_app` with DML + EXECUTE only. Procedures and views are `SQL SECURITY INVOKER`.
4. **Configuration over code** for anything statutory: payroll rules, tax slabs, leave policy, shifts, exit policy are rows editable through APIs.
5. **No monitoring stack** and no test code in this deliverable (explicit requirement).

## 8. Limitations / next steps

* JWT is HS256 with one shared secret (simple, fast); an asymmetric key pair (RS256 / JWKS) would let services verify without being able to mint tokens.
* The e-mail channel runs in LOG mode until SMTP is configured through `/api/v1/notifications/settings/email`.
* Statutory values are samples; gratuity and state-specific professional tax are not modelled.
* Single Kafka broker / single Redis in the compose file (development topology).
