## 1. What and why
**Apache Kafka** is a distributed, durable, partitioned log. Services append events to *topics*; other services read them at their own pace, tracked by *consumer-group offsets*.
Used here so that the employee service need not know who cares about a new hire: auth, organization, leave, attendance, tax, timesheet, performance, reporting and notification each react independently, and a slow or stopped consumer never blocks HR users. It also gives a replayable history (`event_history`, reports).

| Concept | In this project |
|---|---|
| Topic | 24 business topics `domain.event` + `<topic>.DLT` (3 partitions each) |
| Key | employee id → per-employee ordering |
| Producer | `EventPublisher` (common-library) used by each service's `*EventProducer` |
| Consumer group | `hr-<service>`; one `@KafkaListener` method per topic |
| Delivery | at-least-once (`acks=all`, `enable.idempotence=true`) + idempotent consumers = effectively-once processing |

## 3. Producing: the transactional outbox
```java
@Transactional
public Leave approve(...) {
    ... save leave rows ...
    eventPublisher.publish(Topics.LEAVE_APPROVED, employeeId, new HrEvents.LeaveApproved(EventMetadata.of(Topics.LEAVE_APPROVED), ...));
}
```
`publish` inserts an `outbox_events` row (`sent_at` NULL = pending) in the **same DB transaction**, then registers an `afterCommit` callback that sends to Kafka and stamps `sent_at`. If the app dies between commit and send, or Kafka is down, `OutboxRelay` (every 10 s, rows older than 15 s, batch of 50, oldest first) sends the unsent rows later and counts `attempts`. Hence: no event is lost when the data is committed, and no event exists for rolled-back data.
*Expected output:* after approving a leave, `outbox_events` contains the row with `sent_at` filled a moment later, and `kafka-console-consumer` on `leave.approved` prints the JSON shown in `202611251532-sample-messages.md`.

## 4. Consuming: idempotency, retry, DLT
```java
@KafkaListener(topics = Topics.EMPLOYEE_CREATED, groupId = "hr-leave-service")
public void onCreated(String payload) {
    idempotent.handle(payload, HrEvents.EmployeeCreated.class, "leave-employee-created", e -> upsertEmployee(e));
}
```
* `IdempotentEventProcessor.handle` parses the JSON into the record, inserts `(event_id, consumer)` into `processed_events` and runs the work in one transaction; a duplicate insert means "already done" → skipped.
* Failures: `DefaultErrorHandler` retries with exponential back-off (500 ms, ×2, up to 5 s total) and then publishes the record to `<topic>.DLT` (same partition). `IllegalArgumentException` (bad data) is **not retried** - it goes straight to the DLT.
* Notification service uses **non-blocking retry topics** (`@RetryableTopic`, 3 attempts, 1 s ×2): the failing record is parked in a retry topic so later messages are not delayed; the last stop is the `-dlt` topic.
* Out-of-order events across topics (the reporting service sees `leave.approved` possibly before `leave.applied`): facts are upserted with a *status rank* so a later state is never overwritten by an earlier one.

## 5. HR use cases
Onboarding provisioning, org chart, leave → attendance sync, payslip → document registration, resignation → status ON_NOTICE, exit → login revoked + allocations ended, holiday change → attendance snapshot, notifications, reports (full flows in `kafka/202611251532-event-flows.md`).

## 6. Pros / cons
| Pros | Cons |
|---|---|
| Services decoupled in time and knowledge; add a consumer without touching the producer | Eventual consistency: read models lag by milliseconds to seconds |
| Replay and audit history | More moving parts (broker, outbox, ledger tables) |
| Back-pressure is natural (consumer lag instead of failing callers) | At-least-once means every handler must be idempotent |
| Retry / DLT isolate poison messages | DLT needs an operator to inspect and replay |
