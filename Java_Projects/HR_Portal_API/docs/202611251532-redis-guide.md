# Redis Guide

## 1. What and why
Redis is an in-memory key-value store with expiry (TTL) and atomic operations. It is used for data that is **short-lived, hot, or must be shared between service instances**: cached reads, revoked tokens, login-attempt counters, rate-limit buckets, locks and de-duplication markers. MySQL stays the source of truth for everything durable.
Server: container `hr-redis` (`redis:7`), host port **9379**, `appendonly yes`, `maxmemory 256mb`, `allkeys-lru` (`infrastructure/redis/redis.conf`), password from `REDIS_PASSWORD`.

## 2. Usage map
| # | Use | Key pattern | TTL | Written by | Implemented in |
|---|---|---|---|---|---|
| 1 | Spring Cache (JSON values) | `hr:<service>:<cache>:<key>` | per cache, default 10 min | `@Cacheable`, evicted by `CacheEvictor` | `common-library/.../cache/CacheConfig.java`, `CacheEvictor.java` |
| 2 | Revoked access tokens | `hr:auth:revoked:<jti>` | remaining token life | auth `SessionRegistry.revokeToken` | `auth-service/.../SessionRegistry.java`; read by `TokenRevocationChecker` (services) and the gateway decoder |
| 3 | Live sessions per user | `hr:auth:sessions:<userId>` (ZSET jti → expiry) | 1 day | `SessionRegistry` | "log out everywhere" revokes all |
| 4 | Refresh tokens | `hr:auth:refresh:<sha256(token)>` → userId | refresh-token days | `TokenService` | rotation: old one deleted at refresh |
| 5 | Password-reset tokens | `hr:auth:reset:<hash>` → userId | 30 min | `AuthService` | single use |
| 6 | Failed-login counters / lock | `hr:auth:attempts:<username>` | 15 min window, 15 min lock after 5 | `LoginAttemptService` | |
| 7 | Gateway rate limit | `request_rate_limiter.{<key>}.tokens/timestamp` | auto | Spring Cloud Gateway `RequestRateLimiter` | `api-gateway/.../application.yml`, `GatewayBeans.userOrIpKeyResolver` |
| 8 | Distributed locks | `hr:lock:<name>` (random token) | per call | `DistributedLockService.withLock` | `leave-apply:<employeeId>`, `leave-accrual`, `tax-reminders` and other scheduled jobs |
| 9 | Notification de-duplication | `hr:notif:dedup:<dedupKey>` (`SETNX`) | 24 h | notification consumer | `notification-service/.../NotificationService.java` |

### Cache catalogue
| Cache | Service | TTL | Evicted when |
|---|---|---|---|
| `employeeProfile`, `employeeDirectory` | employee | 10 m / 5 m | any employee create / update / status / manager change |
| `departments`, `designations`, `locations`, `departmentTree`, `orgChart` | organization | 30 m / 10 m | master-data change, employee event |
| `leaveTypes`, `leavePolicy`, `leaveBalance` | leave | 30 m / 30 m / 15 m | catalog change, any balance movement |

| `departmentNames` | reporting | 30 m | expiry |

## 3. Code examples
```java
@Cacheable(cacheNames = "employeeProfile", key = "#id")
public EmployeeDetail get(String id) { ... }          // MySQL only on a miss

cache.evict("employeeProfile", id);                     // CacheEvictor after an update

locks.withLock("leave-apply:" + employeeId, Duration.ofSeconds(20), () -> doApply(...)); // one apply per employee at a time
```
`DistributedLockService` acquires with `SET key token NX PX ttl` and releases with a Lua compare-and-delete script, so an expired lock can never be deleted by its previous owner.
Cache values are JSON (Jackson typing is enabled for the final record classes so they deserialize back), readable with `redis-cli`.

## 4. Expected output
```bash
docker exec hr-redis redis-cli -a "$REDIS_PASSWORD" --scan --pattern 'hr:*' | head
# hr:auth:sessions:ca11a6d2-...        hr:employee:employeeProfile::157eaa40-...        hr:auth:revoked:<jti> (after logout)
docker exec hr-redis redis-cli -a "$REDIS_PASSWORD" ttl hr:auth:revoked:<jti>     # e.g. 1534 (seconds left)
```
After logout, replaying the old access token against any endpoint returns `401` with the JSON error body.

## 5. Failure behaviour
* Cache errors are logged and ignored (a `CacheErrorHandler` makes a broken Redis behave like an empty cache).
* Revocation check **fails open** (access tokens live 30 min); the gateway rate limiter fails open.
* Locks fail closed: if Redis is unreachable, the guarded job is skipped / the request gets 503 rather than running unguarded twice.

## 6. Pros / cons
| Pros | Cons |
|---|---|
| Microsecond reads; protects MySQL for hot reads | Staleness up to TTL if an evict is missed |
| TTL gives free cleanup of tokens/counters | Extra component to secure and size (`allkeys-lru` may evict keys, so only recomputable or short-lived data is stored) |
| Atomic primitives (SETNX, Lua, ZSET) for locks and sessions | A single Redis is a single point of failure in the dev topology |
