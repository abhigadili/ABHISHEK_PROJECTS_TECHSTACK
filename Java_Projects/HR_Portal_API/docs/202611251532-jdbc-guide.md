# JDBC Guide

JDBC is the low-level Java API for SQL: `DataSource` → `Connection` → `PreparedStatement` / `CallableStatement` → `ResultSet`. Spring's `JdbcTemplate`, `NamedParameterJdbcTemplate` and `SimpleJdbcCall` remove the boilerplate (connections, exceptions, cleanup) but keep SQL under your control.

**Why alongside JPA?** Stored procedures and functions, recursive CTEs, window functions, batch upserts and aggregates are set-based and awkward through entities. **Rule used everywhere:** values are always bound parameters; SQL text is a constant: nothing user-supplied is ever concatenated into it. Sort columns are validated against an allow-list in `PageRequests` before they reach any query.

| # | Technique | Class (path under `<service>/src/main/java/com/hrportal/...`) |
|---|---|---|
| 1 | Plain JDBC, explicit transaction, batch | `attendance-service/.../jdbc/AttendanceJdbc.upsertHolidays` |
| 2 | `CallableStatement` stored procedure | `AttendanceJdbc.monthlySummary` |
| 3 | `JdbcTemplate.queryForObject` calling SQL functions | `leave/.../LeaveDurationService` (`fn_leave_duration`), `attendance/.../AttendanceService` (`fn_overtime_minutes`), `leave/.../LeaveCalendarService` |
| 4 | `SimpleJdbcCall` for procedures | `leave/.../LeaveBalanceService` (`sp_calculate_leave_balance`), `project/.../AllocationSummaryService`, `timesheet/.../TimesheetReportService`, `exit/.../SettlementService` |
| 5 | `NamedParameterJdbcTemplate` + `RowMapper` + `ResultSetExtractor`, recursive CTE, window function | `organization/.../OrgHierarchyJdbc` |
| 6 | `JdbcTemplate.batchUpdate` + `CALL` | `payroll/.../PayrollRunService` |

## 1. Plain JDBC with an explicit transaction (batch upsert)
**What:** direct use of `Connection`, `setAutoCommit(false)`, `addBatch / executeBatch`, `commit / rollback`. **Why:** the holiday snapshot refresh must be all-or-nothing and fast. **HR use:** `holiday.changed` → attendance refreshes `holiday_snapshots`.
```java
String sql = "INSERT INTO holiday_snapshots (holiday_id, holiday_date, name, location_id) VALUES (?, ?, ?, ?) "
           + "ON DUPLICATE KEY UPDATE holiday_date = VALUES(holiday_date), name = VALUES(name), location_id = VALUES(location_id)";
try (Connection c = dataSource.getConnection()) {
    c.setAutoCommit(false);
    try (PreparedStatement ps = c.prepareStatement(sql)) {
        for (HolidaySnapshot h : holidays) { ps.setString(1, h.getHolidayId()); ... ps.addBatch(); }
        ps.executeBatch(); c.commit();
    } catch (SQLException e) { c.rollback(); throw e; }
}
```
*Expected output:* returns the number of rows in the batch (e.g. `12`); re-running the same list changes nothing (idempotent upsert). On a failure nothing is stored and the API answers `503 Could not store holiday snapshot`.

## 2. CallableStatement
```java
try (Connection c = dataSource.getConnection(); CallableStatement cs = c.prepareCall("{call sp_monthly_attendance_summary(?, ?, ?, ?)}")) {
    cs.setString(1, employeeId); cs.setInt(2, year); cs.setInt(3, month); cs.setNull(4, Types.VARCHAR);
    boolean hasResult = cs.execute();
    while (!hasResult && cs.getUpdateCount() != -1) hasResult = cs.getMoreResults();   // skip update counts to reach the SELECT
    try (ResultSet rs = cs.getResultSet()) { rs.next(); ... }
}
```
**Why the loop:** the procedure first runs an UPSERT (an update count) and then a SELECT. *Output:* `GET /api/v1/attendance/monthly/{employeeId}?year=2026&month=11` → `{"workingDays":21,"presentDays":2,"absentDays":..,"leaveDays":..,"lateMinutes":..}`.

## 3. JdbcTemplate with SQL functions
```java
BigDecimal days = jdbc.queryForObject("SELECT fn_leave_duration(?, ?, ?, ?, ?)", BigDecimal.class, from, to, halfStart, halfEnd, holidays);
```
*Output:* 30 Nov (Mon) - 1 Dec (Tue) → `2.0`; a range covering a Saturday-Sunday adds nothing. The same rule exists once, in the database, and is reused by the application and reports.

## 4. SimpleJdbcCall
```java
this.call = new SimpleJdbcCall(jdbc).withProcedureName("sp_employee_allocation_summary").withoutProcedureColumnMetaDataAccess()
        .declareParameters(new SqlParameter("p_employee_id", Types.VARCHAR), new SqlParameter("p_on_date", Types.DATE))
        .returningResultSet("rows", rowMapper);
Map<String,Object> out = call.execute(Map.of("p_employee_id", id, "p_on_date", date));
```
`withoutProcedureColumnMetaDataAccess()` avoids reading catalog metadata (the runtime user has EXECUTE only).

## 5. NamedParameterJdbcTemplate: recursive CTE and window function
`OrgHierarchyJdbc.reportingChain(employeeId)` walks manager links up to 25 levels:
```sql
WITH RECURSIVE chain AS (
  SELECT employee_id, full_name, manager_id, 0 AS lvl FROM org_employee_nodes WHERE employee_id = :id
  UNION ALL
  SELECT n.employee_id, n.full_name, n.manager_id, c.lvl + 1
  FROM org_employee_nodes n JOIN chain c ON n.employee_id = c.manager_id WHERE c.lvl < 25
) SELECT ... FROM chain ORDER BY lvl
```
`headcountByDepartment()` adds `RANK() OVER (ORDER BY COUNT(n.employee_id) DESC)` and builds the list with a `ResultSetExtractor`.
*Output:* `GET /api/v1/organization/employees/{employeeId}/reporting-chain` → `[{"fullName":"Rahul Verma","level":0},{"fullName":"Priya Sharma","level":1}]`.

## 6. batchUpdate + CALL (payroll)
`PayrollRunService` inserts all payslip lines with one `jdbc.batchUpdate(...)` (hundreds of rows, one round trip per batch) and then `jdbc.update("CALL sp_process_monthly_payroll(?, ?)", runId, user)`, inside **one** `TransactionTemplate` so JPA entities, JDBC batches and the procedure commit or roll back together.

## Pros / cons
| Pros | Cons |
|---|---|
| Full SQL power (CTE, window, procedures), predictable SQL, bulk speed | No dirty checking / caching; mapping by hand |
| Logic that must be identical for every client lives in the DB | Logic is split between Java and SQL - needs migrations and care when changing |
| `PreparedStatement` makes injection impossible for values | Identifiers (table / column names) cannot be bound - so none are ever dynamic here |
| Same `DataSource` and transaction manager as JPA | Hibernate's persistence context is unaware of changes made by procedures → `refresh()` |
