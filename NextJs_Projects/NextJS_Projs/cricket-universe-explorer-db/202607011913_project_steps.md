## Overview

This document covers everything implemented to transform the Cricket Universe Explorer from a static mock-data Next.js app into a fully database-backed application with real authentication, CRUD operations, Swagger API documentation, and advanced MySQL features.

## Part 1 — MySQL Database Setup

### 1.1 Database & Table Creation (`setup_db.py`)

A Python script was written to:
- Connect to MySQL using `subprocess` (running `mysql` CLI with piped SQL)
- Create all tables with proper schema, constraints, and indexes
- Seed all initial data (7 countries, 36 leagues, 14 teams, 38 cricketers, 1 admin user)

**Tables created:**

| Table | Purpose | Key Columns |
|-------|---------|-------------|
| `countries` | Cricket nations | `id` (varchar slug PK), `name`, `short_name`, `flag`, `board`, `captain`, `coach`, `world_cups_won`, `famous_players` (JSON) |
| `leagues` | Cricket competitions per country | `id` (slug PK), `country_id` FK, `name`, `format` (ENUM) |
| `teams` | Franchise teams per league | `id` (slug PK), `league_id` FK, `name`, `captain`, `coach`, `home_ground`, `titles` |
| `cricketers` | Players per team | `id` (slug PK), `team_id` FK, `name`, `role` (ENUM), `batting_style` (ENUM), `runs`, `wickets`, `matches` |
| `loginusers` | User accounts for authentication | `id` (INT PK), `email` (UNIQUE), `password_hash` (bcrypt), `role` (ENUM), `refresh_token_hash`, `is_active` |

**Schema design decisions:**
- String slugs as PKs (`'india'`, `'ipl'`, `'mi'`) for human-readable URLs without joins
- `famous_players` stored as JSON — deliberate 1NF relaxation (see normalization guide)
- `cricketers.country` stored as varchar — denormalized to avoid 3 JOINs in player cards
- `ON DELETE CASCADE` on FK constraints for automatic cleanup
- All tables include `created_at`/`updated_at` timestamps with `ON UPDATE CURRENT_TIMESTAMP`

### 1.2 Data Seeding

Seed data covers:
- **7 countries:** India, Australia, England, Pakistan, South Africa, New Zealand, Sri Lanka
- **36 leagues:** IPL, BBL, PSL, SA20, Super Smash, The Hundred, Sheffield Shield, and more
- **14 teams:** Major franchise clubs (Mumbai Indians, Sydney Sixers, Peshawar Zalmi, etc.)
- **38 cricketers:** Real players with real career statistics (runs, wickets, matches)
- **1 admin user:** `admin@cricket.com` / `Cricket@123` (bcrypt cost=12 hash pre-computed)

| Audit Table | Captures |
|-------------|---------|


#### Cursor Procedure — `sp_cursor_role_run_totals`

Demonstrates:
- `DECLARE CURSOR FOR SELECT ...`
- `OPEN` / `FETCH` / `CLOSE` lifecycle
- `CONTINUE HANDLER FOR NOT FOUND` to exit the loop
- `CASE` statement inside the loop for branching
- Temporary table creation and population
- Returns aggregated role → run totals

#### Window Functions — `sp_window_functions_demo`

Demonstrates:
- `RANK()` / `DENSE_RANK()` — player rankings within each team by runs
- `ROW_NUMBER()` — unique sequential row number per partition
- `SUM() OVER (PARTITION BY ...)` — cumulative runs within each country
- `AVG() OVER (PARTITION BY ...)` — country-level average for deviation analysis
- `NTILE(4)` — dividing teams into quartiles by title count
- `LAG()` / `LEAD()` — comparing each player's runs to adjacent player in ranked list
- `FIRST_VALUE()` / `LAST_VALUE()` — most/least titled team per league

## Part 2 — Next.js API Routes (MySQL-backed)

All API routes replaced mock data with MySQL queries via `src/lib/db.ts` (mysql2 connection pool).

### DB Module (`src/lib/db.ts`)

```typescript
import mysql from 'mysql2/promise'

const pool = mysql.createPool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT),
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  waitForConnections: true,
  connectionLimit: 10,
})

export default pool
```

### Query Module (`src/lib/queries.ts`)

Centralized functions for each entity:
- `getCountries(search?)` / `getCountryById(id)` / `createCountry(data)` / `updateCountry(id, data)` / `deleteCountry(id)`
- Same pattern for `leagues`, `teams`, `cricketers`

Next.js `unstable_cache` wraps read queries with cache tags for revalidation on mutation.

## Part 3 — Authentication System

### Token Architecture

```
Browser              Server                     Database
  │                     │                           │
  │── POST /login ────→ │                           │
  │                     │── getUserByEmail() ──────→│
  │                     │── bcrypt.compare() ────→  │
  │                     │── signAccessToken(15min)   │
  │                     │── signRefreshToken(7d)     │
  │                     │── SHA-256(jti) stored ───→│
  │←── Set-Cookie ──────│                           │
  │   access_token      │                           │
  │   refresh_token     │                           │
```

### Key Implementation Details

| Feature | Implementation |
|---------|---------------|
| JWT library | `jose` (Edge-safe, no Node.js dependencies) |
| Password hashing | `bcryptjs` cost=12 (~300ms hash time) |
| Access token | HS256, 15-min, `ACCESS_TOKEN_SECRET` |
| Refresh token | HS256, 7-day, `REFRESH_TOKEN_SECRET` (different secret) |
| Token revocation | SHA-256(jti) stored in `loginusers.refresh_token_hash`; logout sets to NULL |
| Refresh token rotation | Every `POST /refresh` issues a new RT with a new jti, replaces stored hash |
| Cookie security | `HttpOnly`, `sameSite=lax`, `secure=true` (prod), RT path-restricted to `/api/auth` |
| Route protection | Edge middleware (`src/middleware.ts`) uses `jose.jwtVerify` (Edge-safe) |
| Prevented user enumeration | Login always returns generic "Invalid email or password" |

### Auth Files

| File | Runtime | Role |
|------|---------|------|
| `src/lib/auth.ts` | Edge + Node.js | JWT sign/verify (jose only — no bcrypt) |
| `src/lib/auth-db.ts` | Node.js only | DB queries + bcrypt operations |
| `src/middleware.ts` | Edge Runtime | Cookie verification, route protection |
| `src/app/api/auth/*/route.ts` | Node.js | Auth API handlers |

## Part 5 — Swagger API Documentation

Interactive API documentation at `/api-docs` using `swagger-ui-react` with SSR disabled.

### Modular OpenAPI Spec Structure

```
src/lib/openapi/
├── index.ts          ← assembles full spec; add 1 import + 1 spread per new API
├── schemas.ts        ← reusable component schemas (Country, League, Team, Cricketer, etc.)
└── paths/
    ├── auth.ts       ← /api/auth/* endpoint specs
    ├── countries.ts  ← /api/countries endpoint specs
    ├── leagues.ts    ← /api/leagues endpoint specs
    ├── teams.ts      ← /api/teams endpoint specs
    └── cricketers.ts ← /api/cricketers endpoint specs
```

**Adding a new API (design goal: 2 steps):**
1. Create `src/lib/openapi/paths/my-new-resource.ts` — export a `PathsObject`
2. Add one import + one `...spread` in `src/lib/openapi/index.ts`

Spec served as JSON at `GET /api/openapi`. Swagger UI served at `/api-docs`.
