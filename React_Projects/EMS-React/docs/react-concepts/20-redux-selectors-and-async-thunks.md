# 20 · Redux selectors and async thunks

## 1. Concept explanation
**Selectors** are functions `(state) => value` that read (and derive) data from the store. With `createSelector` (Reselect) they are
**memoised**: the result is recomputed only when its *input selectors'* outputs change, and otherwise the **same reference** is returned
— which is what lets `React.memo`, `useMemo` and chart libraries skip work.

**Async thunks** (`createAsyncThunk`) are functions dispatched like actions that can run async code and dispatch the standard lifecycle
actions `pending → fulfilled | rejected`. They are Redux's tool for *workflows* (commands, multi-step processes), complementing RTK Query
(cacheable reads).

## 2. Syntax
```ts
export const selectKpis = createSelector(selectDashboard, (d) => d ? { total: d.employees.total, … } : null);
const items = useAppSelector(selectHeadcountChart);                 // component subscribes to just that slice of state

export const fetchDashboard = createAppThunk('dashboard/fetch', async (_, { rejectWithValue, signal }) => { … });
await store.dispatch(fetchDashboard());      // returns a promise of the settled action;  .unwrap() throws on rejection
```

## 3. Actual EMS implementation
**Selectors**
| Selector | What it derives | File |
|---|---|---|
| `selectKpis` | KPI cards from `dashboard.data` | `store/selectors/dashboardSelectors.ts` |
| `selectHeadcountChart`, `selectAttendanceChart`, `selectLeaveChart` | chart series arrays (humanised labels) — stable identity feeds `memo(DashboardCharts)` | same |
| `selectEvents` | birthdays/anniversaries with `[]` fallbacks | same |
| `selectDirectoryForDepartment` | employee directory filtered by the **cross-screen department filter** (combines two input selectors) | `store/selectors/employeeSelectors.ts` |
| `directorySelectors.*` | `selectAll/selectById/selectIds/selectTotal` generated by the entity adapter | same |
| `selectLeaveYear`, `selectCalendarMonth`, … | trivial readers | `store/selectors/leaveSelectors.ts` |

**Async thunks** — typed through `createAppThunk` (`store/thunk.ts`)
| Thunk | Notes |
|---|---|
| `bootstrapSession`, `login`, `logout` (`authSlice.ts`) | `rejectWithValue(errorMessage(e))`; `condition` makes bootstrap run once; logout always succeeds locally |
| `fetchEmployeeDirectory` (`employeeSlice.ts`) | loops over pages (`limit: 100`) until `totalPages`; `condition` blocks duplicate loads |
| `fetchDashboard` (`dashboardSlice.ts`) | uses the thunk's `signal` (page unmount aborts it); a **403 is mapped to `forbidden`**, not an error (EMPLOYEE role) |
| `loadToday`, `checkIn`, `checkOut` (`attendanceSlice.ts`) | command workflow; each invalidates the RTK Query attendance tag on success |
| `refreshUnreadCount` (`notificationSlice.ts`) | called by the poller and after read/unread changes |

Pending/fulfilled/rejected are all handled in `extraReducers`; the UI reads `status`/`action`/`error` for spinners, disabled buttons and messages.

## 5. Practical implementation — memoisation you can assert
```ts
it('selectors return the SAME reference until the data changes (memoisation)', async () => {
  await store.dispatch(fetchDashboard());
  const a = selectHeadcountChart(store.getState());
  store.dispatch(setUnread(3));                                 // unrelated state change
  expect(selectHeadcountChart(store.getState())).toBe(a);       // not recomputed → charts don't re-render
});
```
And the department-filter selector: dispatch `setDepartmentFilter(3)` → only "Cara Chen" remains; calling the selector again returns the
identical array. Thunk behaviours covered by tests: pending flag mid-flight, rejection text, `condition` skipping, pagination loop,
and 403→`forbidden`.

## 6. Why the concept is used
Components should receive *ready-to-render* data and re-render only when it truly changed. Thunks keep async orchestration and
error mapping out of components, in a place that is unit-testable with msw.

## 7. Advantages and limitations
**+** derived data computed once and shared; testable pure functions; thunk lifecycle gives free loading/error state; `condition` and `signal` give de-dupe and cancellation. **−** a selector that **returns a new array/object every call** (e.g. `.filter()` in a plain selector) causes needless re-renders and a React-Redux warning — wrap in `createSelector`; memoisation depth is 1 by default (parametrised selectors need a factory); thunks are not a cache (use RTK Query for that); `rejectWithValue` payloads must be serialisable.

## 8. Interview-related considerations
* Why memoise selectors? What does "input selector" mean? When does `createSelector` recompute?
* Reselect vs `useMemo` in the component; selector factories for per-instance parameters.
* Thunk vs saga vs listener middleware; thunk vs RTK Query; `unwrap()`; `condition`; `rejectWithValue`; `AbortSignal`.
* Where should derived data live — state, selector, or component? (Selector/compute, never duplicated state.)
