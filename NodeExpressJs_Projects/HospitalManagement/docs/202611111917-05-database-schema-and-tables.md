# 5. Database schema and table details

MySQL (the **existing** local server, port 3306, user `abhig`), one database per microservice, **Prisma ORM** (one `schema.prisma` per service in `services/<name>/prisma/`, each with its own generated client in `generated/client`). A service only connects to its own database; there are **no foreign keys across databases** - other services' ids (`patientId`, `doctorId`, `userId`, `hospitalId` ...) are plain integers validated through the owning service's API (gRPC / HTTP).

**Total: 39 `hjs_` tables** (+ Prisma's `_prisma_migrations` history table per database). `hjs_outbox_events` / `hjs_processed_events` are the reliable-messaging tables (outbox / inbox).

## These databases are shared with the Java and .NET builds
The Java build created these ten databases first (tables such as `patients`, `users`, `outbox_events`), the .NET build added `hdn_*` tables, and `NotificationDB` also holds tables of other applications (`Notifications`, `sms_*`, `dn_*`, ...). To honour "do not modify or delete existing databases":
* every table of this build is prefixed **`hjs_`** (`@@map("hjs_...")`); Prisma's default FK names (`hjs_<table>_<column>_fkey`) cannot clash with the others' `fk_*` / `fk_hdn_*` names (MySQL constraint names are unique per *database*);
* `CREATE DATABASE IF NOT EXISTS` never recreates anything; nothing outside `hjs_*` and `_prisma_migrations` is read, altered or dropped (verified: HospitalDB still has its 5 Java tables, PatientDB its 3, NotificationDB all its pre-existing tables);
* `_prisma_migrations` did not exist in any of the ten databases beforehand.

## How the schema is created (Prisma migrations)
* `services/<name>/prisma/migrations/20261111000000_init/migration.sql` is generated by `prisma migrate diff --from-empty --to-schema-datamodel` - this is the Prisma **migration** of record; the same SQL (with a `USE <db>;` header) is copied to `database/scripts/` as reference.
* `scripts/create-databases.sh`: runs `database/scripts/00-create-databases.sql` (10× `CREATE DATABASE IF NOT EXISTS`), then per service **baselines safely**: because the databases are not empty, `prisma migrate deploy` would stop with P3005, so the init migration is executed once with `prisma db execute` and recorded with `prisma migrate resolve --applied`. On later runs it only calls `prisma migrate deploy` (applies new migrations, no-op otherwise) - the script is idempotent.
* Evolving a schema: edit `schema.prisma`, run `npx prisma migrate dev --name <change> --schema prisma/schema.prisma` (needs CREATE privilege for the shadow database) or `migrate diff` + `migrate deploy`, commit the migration folder.
* Every service verifies its connection at start-up (`$connect` + `SELECT 1`; a failure is fatal and logged at `fatal`).

## Modelling notes
* **Ids** are `INT AUTO_INCREMENT`; business numbers (`billNumber`, `transactionRef`, `accessionNumber`) have unique indexes. **Money**: `DECIMAL(10,2)/(12,2)`, converted with `Number()` at the DTO boundary and rounded to cents in calculations. **Dates**: `@db.Date` for dates, `"HH:mm"` strings for slot times (lexicographic comparison is correct), `DATETIME(3)` for instants. Enumerations are validated by Zod and stored as short strings.
* **Integrity rules in the schema:** `hjs_patients` unique `userId`/`email`/`phone`/`identityNumber`; `hjs_doctors` unique `licenseNumber`/`email`/`userId`; `hjs_appointments.slotKey` unique while booked (NULL when cancelled/missed, so concurrent bookings of one slot cannot both succeed); `hjs_bills` unique `(referenceType, referenceId)`; `hjs_payments.transactionRef` and `activeBillId` (one in-flight payment per bill); `hjs_pharmacy_orders.prescriptionId`; `hjs_lab_requests.accessionNumber`; `hjs_lab_reports.requestId`; `hjs_record_entries (entryType, referenceType, referenceId)`; `hjs_processed_events (eventId, consumer)`; `hjs_refresh_tokens.tokenHash` (only the SHA-256 of a refresh token is stored).
* **Foreign keys** exist only inside a database: departments→hospitals, schedules/unavailability→doctors, record_entries→patient_records, prescription_items→prescriptions, lab_requests→lab_tests, lab_reports→lab_requests, bill_items/payments→bills, order items→orders/medicines, refresh_tokens→users.
* **Concurrency:** unique indexes for slots/payments/bills; `SELECT … FOR UPDATE` row locks for pharmacy stock inside `prisma.$transaction`.
